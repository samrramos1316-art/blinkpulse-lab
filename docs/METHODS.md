# Methods

_Filled in phase by phase. Numbers here come only from tests or validation runs, with their

## Pipeline overview

```
camera frame (requestVideoFrameCallback, ms timestamp)
  |-- FrameClock: dt, jitter, gap flags ............................ src/capture/frameClock.ts
  |-- MediaPipe Face Landmarker (pre-trained, on device): 478 points  src/vision/
  |     |-- head pose (yaw/pitch vs calibration) -> valid / not valid
  |     |
  |     |-- Stream A, blinks: EAR per eye (pixel coordinates)        src/blink/
  |     |     calibration (10 s) -> close 0.70 b / reopen 0.80 b
  |     |     hysteresis state machine, sub-frame crossings -> blink events
  |     |     -> blink rate, durations, eye-closed fraction (rolling 60 s)
  |     |     -> per-minute timeline (sessionSummary.ts)
  |     |     -> eye-closure indicator: factors vs alert baseline (sleepiness.ts)
  |     |
  |     |-- Stream B, pulse: forehead + both cheek polygons           src/rppg/
  |           mean R, G, B of accepted pixels per frame
  |           every 1 s, per region, last 10 s:
  |             resample to 30 Hz -> POS -> Butterworth 0.7-3.0 Hz (filtfilt)
  |             -> Hann + FFT (4096) -> band peak (parabolic) -> BPM, SQI
  |             -> beat-spacing cross-check, quality flags -> Good / Fair / Poor
  |           fusion of kept regions -> median smoothing -> shown at Fair or better
  |
  `-- nothing is stored; numeric exports only after a user action
```

The Signal Lab view (Phase 5) shows Stream B's steps for one region side by side.

## DSP core (`src/dsp/`, Phase 1)

All signal processing is hand-written TypeScript with no DSP libraries. It is checked against
SciPy 1.17.1 / NumPy 2.4.6 reference outputs generated by `tools/gen_fixtures.py` (fixtures
committed in `test/fixtures/`). "Relative error" below means max |ours - reference| divided by
max |reference|, which stays meaningful where the reference passes through zero.

| Module           | Method                                                                                               | Reference check (tests)                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `fft.ts`         | Iterative radix-2 Cooley-Tukey (decimation in time), direct cos/sin twiddle table                    | `numpy.fft.fft` / `rfft`, 6 cases: worst relative error 7.2e-16; also vs a naive DFT          |
| `window.ts`      | Hann (symmetric and periodic), rectangular, coherent gain, ENBW                                      | `scipy.signal.windows.hann`, 10 cases                                                         |
| `butterworth.ts` | Analogue prototype, cutoff pre-warping, bilinear transform, conjugate-pair sections                  | `scipy.signal.butter(..., output='sos')`, 17 designs: worst relative error 3.3e-16            |
| `biquad.ts`      | Direct form II transposed; `filtfilt` with odd-extension padding and steady-state initial conditions | `sosfilt`, `sosfilt_zi`, `sosfiltfilt`, `sosfreqz` on 3 filters: worst relative error 2.0e-14 |
| `resample.ts`    | Linear interpolation; bin averaging (centroid-timed) at >= 1.5x the target rate                      | Synthetic sines with timing jitter, 3 cases                                                   |
| `stats.ts`       | Mean, std, median, percentile, linear detrend, MAD                                                   | NumPy and `scipy.signal.detrend`                                                              |
| `peaks.ts`       | Local maxima, distance and prominence filters                                                        | `scipy.signal.find_peaks` / `peak_prominences`, 5 cases (exact indices)                       |
| `spectrum.ts`    | Linear detrend, periodic Hann, zero-padded FFT, parabolic interpolation of log power                 | Synthetic sines (below)                                                                       |

### Butterworth design

Same steps as `scipy.signal.butter`:

1. Prototype poles `p_m = -exp(i*pi*m/(2N))`, `m = -N+1, -N+3, ..., N-1`.
2. Pre-warp the cutoff: `warped = 2*fs' * tan(pi*Wn/fs')` with `fs' = 2` and `Wn = fc/(fs/2)`.
   This puts the digital -3 dB point exactly at the requested cutoff.
3. Low-pass: scale the poles by `warped`. High-pass: `p -> warped/p`, plus N zeros at `s = 0`.
4. Bilinear transform `z = (2fs' + s)/(2fs' - s)`; zeros at infinity go to `z = -1`.
5. Each conjugate pole pair becomes one section. Poles closest to the unit circle go last, and
   the overall gain goes in the first section (SciPy `zpk2sos`, `pairing='nearest'`).

Only even orders are implemented (every pole then has a conjugate partner). The spec needs 2 and 4.

**Band-pass** = 4th-order high-pass at 0.7 Hz followed by 4th-order low-pass at 3.0 Hz (8 poles,
the same pole count as SciPy's `butter(4, [0.7, 3.0], 'bandpass')`). Designed magnitude at
fs = 30 Hz (from `sosMagnitudeDb`, asserted in `filters.test.ts`):

| Frequency | 0.1 Hz   | 0.7 Hz   | 1.5 Hz   | 3.0 Hz   | 8 Hz     |
| --------- | -------- | -------- | -------- | -------- | -------- |
| Gain      | -67.7 dB | -3.01 dB | -0.02 dB | -3.01 dB | -42.7 dB |

`filtfilt` runs the filter forward and backward, so its magnitude is squared (about -6 dB at the
cutoffs) and its phase is zero.

### Spectrum and peak frequency

Power spectrum: linear detrend, periodic Hann window, zero-pad to `nfft` (4096 for pulse),
one-sided power scaled so an on-bin sine of amplitude A reads A^2/2. The peak in a band is
refined by fitting a parabola to the log power at the maximum bin and its two neighbours.

**Resolution note.** The true frequency resolution is about 1/T: 0.1 Hz (6 BPM) for a 10 s
window. Zero padding only interpolates between those points, and parabolic interpolation refines
the peak location. Real accuracy therefore depends on signal-to-noise ratio, not on padding
length. On clean synthetic sines (10 s at 30 Hz, 0.70-3.00 Hz in 0.01 Hz steps, 4 phases each,
n = 924) the worst frequency error was 0.0007 Hz. That describes the method on noise-free input;
it is not a measure of pulse-rate accuracy, which will come from validation V2.

### Resampling

Frame timestamps are irregular. Samples are moved onto a uniform grid (30 Hz for pulse) by:

- **Linear interpolation** when the source rate is below 1.5x the target.
- **Bin averaging** otherwise: average the samples in each bin of +-half a grid step, keep each
  average at the mean time of its samples, then interpolate onto the grid. Keeping the mean time
  removes the timing error a plain bin average has when jitter moves samples across bin edges
  (in testing, 60 fps input with 4 ms jitter gave errors of about 6% of the sine amplitude at
  1.3 Hz before this change). The averaging reduces aliasing: a 25 Hz tone sampled at 60 fps
  lost more than 6 dB at its 5 Hz alias compared with linear interpolation (test).
- Grid points inside a source gap longer than `maxGapMs` are marked invalid (NaN), never filled.

## Capture and timing (`src/capture/`, Phase 2)

### Camera request

`getUserMedia` is called with exactly the PROJECT_SPEC 5.1 constraints (640x480 ideal, frame rate
ideal 60 with a minimum of 24, front camera, no audio). If no camera can meet the 24 fps minimum
the browser rejects with `OverconstrainedError` (MDN: `min` is mandatory), and the request is
repeated once without the minimum. The UI then says the camera runs below 24 fps. The actual
settings come from `track.getSettings()` and are shown in Timing details.

### Frame timestamps

Frame callbacks come from `HTMLVideoElement.requestVideoFrameCallback` when the browser has it
(feature-detected; callbacks are one-shot and re-registered each frame, per the WICG spec). The
timestamp source is chosen on the first frame and kept:

1. `captureTime`, if present and within 1000 ms of the callback's `now`. The spec does not state
   its time base, so a value on another clock is rejected rather than mixed in.
2. `presentationTime`.
3. `mediaTime` x 1000, only if positive (it can be 0 for live streams).
4. Without `requestVideoFrameCallback`: `requestAnimationFrame` + `performance.now()`. This fires
   per display refresh, so frames can repeat or be skipped; it is a fallback only.

If the chosen source disappears mid-session, the next best source is used and the switch is
recorded as a gap (`sourceChange`), because the two clocks are not comparable.

### FrameClock

`FrameClock` (pure, unit-tested) turns raw timestamps into milliseconds since the first frame.
Timestamps that do not increase are rejected, so `tMs` is strictly increasing. Over the last 90
intervals it reports:

- **Median interval** and **jitter** (population standard deviation of the intervals that are not
  gaps).
- **Measured rate** = 1000 / mean interval. The mean is used, not the median: camera intervals can
  be skewed, and 1000 / median then overstates the delivered rate (see the measurement below).
- **Irregular intervals**: longer than 1.5x the rolling median (the original PROJECT_SPEC 5.1 gap
  rule). Counted and shown as a timing warning; they do not invalidate data.
- **Gaps** (real breaks): an interval longer than 2.5x the rolling median, frames reported dropped
  (below), a hidden tab, or a timestamp-source change. Each gap is stored as a time interval;
  `spansGap(gaps, start, end)` lets later stages reject any blink event or pulse window that
  overlaps one. Hidden-tab and source-change pauses are not added to the rolling statistics.
  Since 2026-10-24 (author's decision, note in PROJECT_SPEC 5.1), a skipped frame or a long
  interval breaks an analysis only when the hole is longer than its own limit (100 ms for blinks
  and the eye-closure indicator, 250 ms for pulse; `breaksAnalysis`); a hidden tab or a source
  change always does.
  This split is option A, approved by the author on 2026-10-17 (note in PROJECT_SPEC 5.1),
  because the 1.5x rule flagged 3-6% of intervals on a complete stream (table below). The 2.5x
  factor is provisional until real webcams are measured in Phase 4.

**Dropped frames** are counted from `presentedFrames` in the frame-callback metadata: a jump of
more than 1 between callbacks means frames were shown without reaching the app, and that interval
becomes a gap. This is only available with `requestVideoFrameCallback`. An earlier estimate from long intervals
(`round(dt / typical dt) - 1`) was removed: on the fake camera below it reported 4 to 13 drops per
run while `presentedFrames` showed none, because each long interval was followed by a short one
(intervals ranged from 11 ms to 55 ms around a 33.3 ms mean).

### Hidden tab

On `visibilitychange` to hidden, frames are ignored (analysis paused) and the pause is recorded
as a `hidden` gap. The status line shows "Keep this window visible (e.g. side-by-side) for
measurements." while hidden and a "Paused while this window was hidden" note afterwards.

### Browser measurement (fake camera)

Headless Chrome with its built-in fake camera at 30 fps (`--use-fake-device-for-media-stream=fps=30`),
production build, 3 runs of 10 s (about 310 frames each). An independent recorder on the same
`<video>` element logged raw `captureTime` values next to the app:

| Run | Independent: mean / median interval | Independent: intervals > 1.5x median | App: measured rate | App: new gaps | App: dropped frames |
| --- | ----------------------------------- | ------------------------------------ | ------------------ | ------------- | ------------------- |
| A   | 33.31 / 31.40 ms                    | 10 (all 47-50 ms)                    | (before fix) 31.9  | 11            | 0                   |
| B   | 33.33 / 31.70 ms                    | 17 (48-55 ms)                        | 29.9 fps           | 19            | 0                   |
| C   | 33.32 / 32.00 ms                    | 13 (48-54 ms)                        | 29.9 fps           | 12            | 0                   |

The app's gap count tracks the independent count (it uses a rolling rather than a global median,
so small differences are expected). Before the fix, run A showed 31.9 fps from 1000 / median for
a stream delivering 30.0 fps.

Runs A-C used the 1.5x rule as the gap rule ("new gaps" = intervals over 1.5x). After option A,
one more 10 s run (independent: mean 33.29 ms, 16 intervals over 1.5x the median) showed 30.1 fps,
14 irregular intervals, 0 gaps, and 0 dropped frames; a simulated hidden-tab pause then added
exactly 1 gap.

This is Chrome's synthetic camera, not a real webcam. Real cameras have not been measured yet.

### Eye aspect ratio

EAR = (|P2 - P6| + |P3 - P5|) / (2 |P1 - P4|), on **pixel** coordinates (normalised x and y have
different scales; a unit test shows normalised space distorts EAR on a 4:3 frame). The per-frame
value is the mean of both eyes; each eye is kept for the Timing details and the V1 export.

### Calibration

10 s of valid samples: `b0 = median`, `b = median(samples >= 0.85 b0)`, close threshold `0.70 b`,
reopen threshold `0.80 b` (PROJECT_SPEC 5.3). Fewer than 100 valid samples asks for a retry. The
median head pose during calibration becomes the reference for head-pose gating.

### Blink detector

Hysteresis state machine (open, closed, reopening). Start and end times are linear interpolations
of the close- and reopen-threshold crossings between frame timestamps. Events are classified by
duration: blink (< 500 ms), long closure (500-2000 ms), extended closure (> 2000 ms). An event with
only one sample below the close threshold is marked low confidence. An invalid sample (no face,
head turned), a hole over 100 ms, a hidden tab, or a timestamp-source change aborts the event in
progress. A single skipped frame at 30 fps (a 67 ms hole) is bridged (since 2026-10-24; before, it
aborted the event).

### Head-pose gating (deviation from PROJECT_SPEC 5.3)

Yaw, pitch, and roll come from the facial transformation matrix (R = Ry Rx Rz). Samples are
rejected when the pose differs from the **calibration reference pose** by more than 25 deg yaw or
20 deg pitch. The spec's limits are absolute, but in the first live test (one person, one laptop
webcam) normal viewing read about 19 deg pitch because the camera sits below eye level, so most
frames were rejected and calibration never finished. There is no pose gating before or during
calibration.

### Metrics

Over the last 60 s: blink rate = (blinks + long closures) per minute of **valid** time; eye-closed
fraction = closed time of all events / valid time; last and median blink duration. Nothing is shown
before 20 s of valid time. Durations are accurate to about +-1 frame interval.

### Synthetic tests (PROJECT_SPEC 6.3)

Generated EAR sequences with known event times (`tools/synth.ts`: seeded noise, truth by bisection
on the noise-free signal), scored with `matchEvents` (+-100 ms on start time):

- Clean blinks at 24, 30, and 60 fps, 15 blinks each (n = 45): precision 1, recall 1, every
  duration error below one frame interval.
- Noisy baseline (sd 0.01) with 3 ms timestamp jitter, 24/30/60 fps, 15 blinks each (n = 45):
  precision 1, recall 1, every duration error below one frame interval.
- Single cases: fast blink of about 116 ms at 24 fps is found; slow 400 ms blink is one event;
  1 s and 3 s closures are classified; a single-frame dip is reported with low confidence; a squint
  above the close threshold is not an event; hysteresis keeps a wobbling closure as one event;
  baseline drift of -0.03 per minute keeps precision and recall at 1; gaps over 100 ms and invalid
  samples abort events, a single dropped frame does not.

These are tests of the detector logic on idealised signals, not of accuracy on real video
(validation V1).

### Setup hints and EAR plot

- Positioning hint (one at a time): face not found, "Move a little closer" when the outer-eye-corner
  distance is under 0.12 of the frame width, "Move back a little" over 0.40, then lighting. These
  limits are untested UI heuristics.
- The EAR plot is drawn on a canvas from the pipeline's 20 s ring buffer (no chart library). Gaps
  break the line; thresholds use distinct dash patterns with text labels; events are shaded bands.
  A text description is available under "Describe this plot".

### Validation V1 tool (`#v1`)

Plays a local video file and runs the same pipeline on every frame using
`requestVideoFrameCallback` `mediaTime` as the timestamp, so detections and hand labels share the
video's own timeline. Calibration uses the first 10 s; labels inside that window are excluded from
scoring. Frames skipped by the player (`presentedFrames` jumps) are counted and marked as gaps
(holes up to 100 ms are bridged, as in the live app); if any occur, analyse again at a lower speed. Labelling is frame by frame with the detections hidden.
Exports (numbers only): detections, labels, and per-frame EAR CSV. Scoring (`src/blink/v1.ts`) is
shared by the page and `npm run score:v1`.

## Session timeline (`src/blink/sessionSummary.ts`, Phase 3b)

Per SPEC_AMENDMENT_01 Patch B. The session starts with the first frame after the first
calibration and is cut into one-minute bins.

- **Valid time** uses the same rule as the 60 s metrics: intervals between consecutive valid samples
  without a gap (<= 100 ms, and no hidden-tab or source-change break), split exactly at minute
  boundaries.
- **Lost time** is attributed per interval: a gap (> 100 ms, or a hidden-tab or source-change
  break) counts as "gap"; otherwise the reason of the invalid sample (face not found, head turned,
  calibrating during a recalibration).
- **Events** belong to the minute in which they start; closed time is split across minutes.
- **Usable** when valid time is at least 70% of the full minute (Patch B). The current minute is
  therefore unusable until 42 s of it are valid. Unusable minutes report no values (gaps in plots,
  "-" in the table, empty cells in the CSV), never zeros. A usable minute without blinks reports a
  count of 0 and no duration.
- Per usable minute: blink count (blinks + long closures), rate per valid minute, median and mean
  duration, long and extended closures, eye-closed fraction (all kinds / valid time). Each minute
  also records its median frame interval; below 24 fps (the camera minimum in PROJECT_SPEC 5.1)
  it is marked low frame rate.
- Synthetic test (5 minutes at 30 fps, noise sd 0.005, 2 ms jitter, one run): a 30 s face dropout,
  a 25 s head turn, and a 20 s frame gap each made their minute unusable with the right reason, and
  lost time matched the injected durations to within 0.5 s. In the two usable minutes (n = 12 and
  n = 8 events), counts and long-closure counts matched the truth exactly, median duration was
  within 34 ms, and eye-closed fraction within n x 34 ms / 60 s of the truth.
- The view shows four per-minute plots (rate, median duration, eye-closed fraction, long
  closures), a coverage bar (solid vs hatched), a per-minute table, and text descriptions of each
  plot. Export asks for confirmation and states what the file contains.

### Pixels

For each region, only its bounding box is drawn from the video into a small canvas
(`willReadFrequently`) and read with `getImageData`; the polygon mask is applied in code (pixel
centres, even-odd rule). Rejected pixels: any channel >= 250 (saturated) or luma < 20 (dark). Per
frame: mean R, G, B of accepted pixels, mask coverage (accepted / polygon pixels), saturated
fraction, mean luma. Frames with no face or a head pose outside the calibration-relative limits are
not used.

### Chain (per region, every 1 s, 10 s window)

1. Resample to 30 Hz (bin-averaging from >= 45 fps, else linear). A hole > 250 ms, a FrameClock
   break of more than 250 ms, a hidden page or a change of timestamp source, or data missing at
   either end invalidates the window. Shorter FrameClock breaks (a skipped frame, an interval over
   2.5x the median) are bridged by resampling (`pulseGapBefore`, fixed 2026-10-23: before, every
   skipped frame invalidated all regions for 10 s).
2. POS exactly as in PROJECT_SPEC 5.4 (window round(1.6 fs) = 48 samples, overlap-add).
3. Butterworth band-pass 0.7-3.0 Hz (the Phase 1 design: -3.01 dB at both cut-offs, -67.7 dB at
   0.1 Hz, -42.7 dB at 8 Hz, single pass), applied with `filtfilt`.
4. Linear detrend, Hann window, zero-pad to 4096, FFT; strongest peak in 0.7-3.0 Hz with parabolic
   refinement of log power; BPM = 60 f. Resolution: a 10 s window resolves about 1/T = 0.1 Hz
   (6 BPM); zero padding only interpolates the spectrum, so accuracy depends on signal-to-noise
   and interpolation, not on the padding length.
5. SQI = (power within +-0.1 Hz of the peak + within +-0.1 Hz of its second harmonic) / power in
   0.7-3.0 Hz. Harmonic power counts only inside the band, so the SQI stays in 0..1.
6. Time-domain cross-check: peaks of the filtered signal (minimum spacing 0.33 s, prominence >=
   0.5 SD of the signal), BPM = 60 / median inter-beat interval (needs 3 peaks). A difference
   > 8 BPM lowers the quality one step.

### Quality and fusion

- Levels from the SQI: Good >= 0.7, Fair >= 0.5, else Poor. Each of motion, sudden lighting
  change, frame rate < 20 fps, and cross-check disagreement lowers the level one step. Below
  15 fps there is no estimate.
- How the SQI levels were set (synthetic data only, 10 s windows):
  - Noise-only windows at 30 fps (no pulse, n = 400): SQI median 0.276, 95th percentile 0.446,
    99th percentile 0.517, maximum 0.589.
  - Pulse windows at 24/30/60 fps, noise sd 0.3-1.0, 5 rates from 50 to 170 BPM (n = 900): of the
    windows with SQI >= 0.4, 2.7% were off by more than 5 BPM; with SQI >= 0.5, 0% (372 kept).
  - Frozen before V2b (PROJECT_SPEC 7.1), not tuned on its results.
- Other starting values (untested): region flags at saturated fraction > 5%, mean luma < 40,
  mask coverage < 60% (Patch A); lighting change at a frame-to-frame luma change > 5%; motion when
  more than 10% of the window's frames move the nose tip (landmark 1) faster than 0.5 inter-ocular
  distances per second (outer eye corners 33 and 263).
- Fusion as Patch A: keep Fair-or-better regions without region flags; SQI-weighted median;
  agreement = max - min; one region caps the level at Fair; agreement > 8 BPM lowers it one step.
  A value is shown only at Fair or better.
- Smoothing: median of the last 5 accepted estimates; an estimate > 12 BPM from that median is
  held and accepted (with the held one) only if the next is within 6 BPM of it (the 6 BPM is a
  starting value). After 5 hops without a shown value the history is cleared. With no history
  (start, or after that reset) the first estimate is shown only when the next agrees within
  6 BPM (SPEC_AMENDMENT_03 D2). A hop without a usable estimate drops any held estimate, so
  confirmation always comes from the next hop.
- Pooled-region fallback (SPEC_AMENDMENT_03 D1): when the fusion has no Fair-or-better value, the
  usable regions without region flags (at least 2) are pooled: at frame times present in every
  pooled region, each channel divided by that region's window mean, averaged with equal weights.
  The pooled trace goes through the same chain and quality rules, capped at Fair, and is used only
  at Fair. The UI and the estimates CSV (`pooled_*` columns) say when it was used.

- 10 s windows, noise sd 0.2, +-3 ms jitter, drift 5%/min, rates 50/72/95/130/170 BPM x 10 seeds

## Eye-closure indicator (`src/blink/sleepiness.ts`, Phase 4B, normal use)

Implements the draft `docs/STUDY_PROTOCOL.md` Sections 3-7. The protocol is **not frozen**: these
constants can still change before a study, and nothing here has been tested on people.

- **Input:** the same per-frame EAR, validity, and gap flags as the blink cards, from calibration
  on; and the detector's blink events. Each frame interval is classified once (open, closed
  (EAR <= 0.20 b), face lost, head turned, gap). A window sums the intervals that end inside it; a
  ~33 ms interval is not split at the window edge.
- **Factors:** closed fraction; closures of 500 ms or more per valid minute; mean duration of
  blinks under 500 ms. Blink rate (blinks + long closures per valid minute, as on the card) is shown
  as a ratio but is not in the index.
- **Alert baseline:** started by the user after calibration with a confirmation; 3 minutes of
  valid time within 6 minutes of clock time and at least 10 blinks, otherwise it fails with the
  reason. Cleared by recalibration; kept across a camera restart; memory only.
- **Index:** `ECI = mean of min(max(X, floor) / max(X0, floor), 5)` over the three factors, with
  floors 0.01, 0.2 per minute, and 100 ms. Equal to exactly 1 for a window identical to the
  baseline (tested).
- **Gating:** valid time >= 70% of the window, median frame rate >= 24 fps, at least 3 blinks
  under 500 ms; otherwise "Not enough data" with the reason, and a gap in the trend.
- **Windows:** 60 s and 5 min, both evaluated every 10 s after the baseline. The card shows the
  5-minute value with the band label and a gauge (position and tick marks, not colour); bands use
  the provisional cut-offs 1.5 and 2.5, labelled as unvalidated in the Eye closure tab.

**Tests** (`src/blink/sleepiness.test.ts`, 21; `src/app/blinkPipeline.test.ts`, 2 more;
UI model and panel tests, 9), all on synthetic sequences at 30 fps with open EAR 0.30:

- Baseline of one 150 ms blink every 4 s: closed fraction 0.0375 (within 0.005), 15 blinks/min,
  mean 150 ms, no long closures.
- Same behaviour after the baseline: ECI within 0.05 of 1, band "Near your baseline".
- Blinks of 300 ms plus one 800 ms closure per minute: duration ratio 2, long-closure ratio 5
  (capped), closed-fraction ratio 2.36, ECI 3.12 (each within 0.05), band "Well above".
- Blink duration rising 150 to 400 ms over 11 minutes: the 5-minute ECI never falls by more than
  0.01 between 10 s steps and rises by more than 0.5 overall.
- "Not enough data", never a number, for: no calibration, no baseline, face lost for half the
  window, head turned for 60% of it, frame gaps, 20 fps, fewer than 3 blinks, and a window longer
  than the recorded time.
- Changing only the blink rate leaves the ECI unchanged.

**Browser check** (production build, headless Chrome, synthetic face without blinks as the
camera): card and tab texts before calibration, after calibration, and while recording the
baseline (13% after 30 s); the confirmation gets focus; after about 3 minutes the baseline failed
with "too few blinks", as expected for a face that never blinks. No external requests, no errors.
The trend plots, gauge, and summary with real values were checked only in unit and server-render
tests, because the synthetic face cannot blink.

## Study mode (`src/study/`, `#study`, Phase 4B)

Implements PROJECT_SPEC 5.8 and the draft `docs/STUDY_PROTOCOL.md` Sections 8-10. The protocol is
**not frozen**, and the rating wording is a placeholder until the KSS permission (decision D2), so
study mode is for testing on oneself only.

- **Clock:** the session (steps, ratings, PVT-B) uses `performance.now()`. The blink pipeline uses
  frame time, which starts at 0 with each camera session, so blink events, the analysis windows,
  and the trend are converted with the capture's offset between the two clocks (frame timestamps
  from `captureTime` or `presentationTime` are on the `performance.now()` clock, so the offset is
  exact; with `mediaTime` it includes the frame's delivery delay). The export records the
  timestamp source so a session that fell back to `mediaTime` can be excluded. Before 2026-10-21
  this conversion was missing: the windows were placed by the time from page load to the first
  camera frame too late, and events and the trend were exported on the wrong clock (found in a
  code review; no study data had been collected).
- **Steps** (`session.ts`, a pure state machine driven by a 250 ms timer): setup (participant
  code, session number, glasses, consent check) -> blink calibration -> first rating -> alert
  baseline (the indicator's baseline rules; a failure ends the session with the reason) -> PVT-B
  -> 25-minute work block with a rating at 5, 10, 15, 20, and 25 minutes -> PVT-B -> finished.
  An unanswered rating closes after 60 s and is recorded as missing; the second PVT-B starts only
  after the last prompt is answered or times out. The session can be stopped at any step, and it
  ends if the camera stops after calibration.
- **Rating prompt:** nine buttons in a corner box that does not take keyboard focus; the window
  title changes while it is open so it shows in the taskbar. The first rating is a full panel.
- **PVT-B** (`pvt.ts`): the counter is written to the DOM from animation frames; the stimulus
  onset is the frame time, the response time the key or pointer event's `timeStamp`. Lapse
  RT >= 355 ms or no response in 30 s; false start RT < 100 ms or a response with nothing showing;
  the next stimulus 1-4 s (uniform) after each response, including the 1 s feedback; a stimulus
  still showing at 3:00 is not scored. Space or a tap on the box; the box gets focus at the start
  so Space cannot press another button. No flashing: only the number changes.
- **Analysis windows:** the 5 minutes before each work-block prompt appears, and each PVT-B run,
  evaluated with the indicator's gating 5 s after they end (blink events arrive when the eye
  reopens). Events are kept 60 s beyond the 5-minute window so a late evaluation sees the same
  data (tested).
- **Blinding (SPEC_AMENDMENT_01 C3, draft decision D5):** during a session the screen shows only
  the step, instructions, and a text face status. The indicator, its factors and bands, the blink
  and pulse cards, the EAR plot, and the camera preview are not rendered; the preview's video stays
  in the page at 1 px (clipped) because measuring needs it. The review (indicator tab, blink
  timeline, reaction-time summary, ratings) appears only after the export.
- **Export** (`studyCsv.ts`, format `blinkpulse-study-1`): `# key=value` header lines (app commit,
  participant code, session, local start time, time slot, glasses, display rules, rating wording,
  end reason, timestamp source, camera size and rate), then `#section=` tables: steps, calibration,
  baseline (with the first rating and the "not alert" flag for a rating of 6 or more), ratings,
  windows, trend (both windows every 10 s), events, PVT-B trials, PVT-B summaries. Times are ms
  since the session start. Every eye-closure row has coverage, lost time by reason, and the median
  frame rate; a failed window has its reason and empty factor cells, never a number.

**Tests:** `pvt.test.ts` (11): onset at the showing frame, RT from event time, feedback 1 s, next
stimulus 1-4 s after the response over a full seeded run, lapse at 355 ms but not 354 ms, false
starts (no stimulus, 99 ms, negative RT) restart the interval, 30 s timeout, end at 3:00 with an
unscored last stimulus, summary statistics. `session.test.ts` (12): step order, prompt timing,
60 s time-out, last prompt before the second PVT-B, window bounds, settled evaluation, baseline
failure, stop, export flag, rating range, participant-code format, time slots.
`studyCsv.test.ts` (9): header values, sections, relative times, missing ratings, failed windows
without numbers, trend limited to the session, PVT-B summaries, every cell a number or short code,
"not alert" flag. `StudyScreen.test.tsx` (15): for every step from setup to finished, the rendered
page has no indicator title, subtitle, band, or factor label and no blink, closed-fraction, or
pulse card; the preview is hidden except during calibration; the review appears only after the
export. `sleepiness.test.ts` (+2): a window evaluated 30 s late equals the on-time result; lost
time and frame rate per window.

**Browser check** (2026-10-19, production build, headless Chrome; the camera was a synthetic
rendered face that closes its eyes for 5 frames every 4 s, i.e. 15 blinks/min, as a looping
video; no real person): the main app measured 15 blinks/min (median duration 212 ms for 167 ms
drawn closures). One full study session (34.5 min): every step in order; a typed name was
refused as a participant code; the alert baseline finished at 3:10 (36 blinks, 12/min); five
prompts at 5-minute steps, one left unanswered and recorded as missing after 60 s, the window
title changed while each prompt was open; seven analysis windows all passed gating, with ECI
0.98-0.99 for unchanged behaviour; on every step the page text had none of the indicator, band,
factor, blink, closed-fraction, or pulse labels and the preview was hidden after calibration;
the review appeared only after the export; no errors, no external requests. In that run the test
script pressed Space 1-25 ms after each number appeared, so every response was correctly scored a
false start. A second run to the first PVT-B with responses about 200 ms and 420 ms after the
number appeared, and one stimulus left unanswered: RTs of about 216-229 ms (the script's own delay
adds about 25 ms), 420 ms responses and the 30 s non-response scored as lapses (14 of 53 stimuli),
median RT 225.8 ms; the session was then stopped and exported with `end_reason=stopped`. These
check the plumbing only; they say nothing about the RT accuracy of a real display and keyboard.

## V3 analysis script (`tools/analyze_v3.py`, Phase 4B)

Implements `docs/STUDY_PROTOCOL.md` Sections 7-9 on the study-mode CSV files (Python, `tools/`
only, NumPy 2.4.6 and SciPy 1.17.1 as pinned in `tools/requirements.txt`).

```sh
.venv/Scripts/python tools/analyze_v3.py data/ --dev P01 --out report.md   # held-out analysis
.venv/Scripts/python tools/analyze_v3.py data/ --dev P01 --bands           # band rule (Section 7)
.venv/Scripts/python -m unittest tools/test_analyze_v3.py                  # tests
```

- **Reading:** the `blinkpulse-study-1` format (`# key=value` header lines, `#section=` tables).
  A file with another format, or the same participant and session twice, stops the script.
- **Exclusions (Section 8), in order:** no blink calibration; no alert baseline; work block
  shorter than 15 minutes. A rating is usable when it was answered and its 5-minute window passed
  gating. A participant is analysed with at least 5 usable ratings and 2 different values. Every
  exclusion is listed in the report with its reason.
- **Formula check:** the ECI is recomputed from the exported factors and baseline with the
  Section 5 floors and cap, and every exported value must agree within 0.001 (the export rounds
  to 4 decimals). This also checks that the Python formula matches the app's `eciFromFactors`.
- **H1 and controls:** Spearman rho (average ranks) per participant for the ECI, time on task
  (minutes from the start of the work block to the prompt), and blink rate (the window's blinks
  per valid minute) against the rating; 95% percentile bootstrap intervals from 10,000 resampled
  pairs (D14 for constant resamples); one-sided Wilcoxon signed-rank test on the ECI rhos; for
  each control, the median of rho(ECI) - rho(control) with a 10,000-resample bootstrap interval
  over participants, and the Section 1 rule ("adds nothing" when the interval includes 0).
- **H2:** end minus start PVT-B for the ECI and the raw factors (D16), two-sided Wilcoxon across
  sessions with both windows usable; Spearman of the PVT-B-window ECI with lapses, median RT, and
  mean 1/RT over all runs (D18), with bootstrap intervals.
- **Sensitivity:** participant-level baseline (the session with the lowest baseline rating, the
  lower session number on a tie; ratios recomputed offline), without "baseline not alert"
  sessions, and the 60 s window (D15). Exploratory pooled AUC for ratings of 7 or more (D17).
- **Bands:** the 95th percentile (linear interpolation) of the development participants' 5-minute
  ECI at ratings of 4 or less; final cut-offs only with at least 20 such windows and P > 1.
- **Reproducibility:** one NumPy generator seeded with 20261017; the same files give the same
  report (tested). The report states the app commits and the rating wording of the files, and
  warns when the wording was the placeholder.

**Tests** (`tools/test_analyze_v3.py`, 17, all passing on 2026-10-20): reading a file written by
the app's own export code (`test/fixtures/study/blinkpulse-study-P90-S1.csv`, kept in step with
the format by `test/studyFixture.test.ts`); the formula against the app's values, floors and cap;
the vectorised Spearman against SciPy on 50 random cases; redraws of constant resamples; AUC;
six synthetic participants whose ratings rise with the ECI out of time order (rho = 1 each,
Wilcoxon p = 1/64, time-on-task control interval excludes 0); the same with the ECI reversed
(reported as not supported); each session and participant exclusion; development participants
left out; duplicate sessions rejected; the participant-level baseline choice; the 60 s trend
lookup; the band rule with fewer than 20 and with 20 windows; a deterministic report.

**Not verified:** any real study data (none exists; the protocol is not frozen).
